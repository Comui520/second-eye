# 规格价格、多媒体证据、受控流水线与交互升级设计

日期：2026-10-26

基线：`f728ff8` / v0.1.1
版本：修订版 2（追加资源配置、流水线与全站交互要求）

状态：用户已批准修订设计；正在编写实施计划，尚未开始实现。

## 1. 目标与已确认范围

用户确认采用方案 A：分阶段实施，完成规格与价格可信度、多媒体分析，再进行全项目检查、性能优化及缺陷修复。
重点是同一商品链接中的型号／容量组合，以及“标价不代表实际售价、需要询价”的商品。
继续沿用 Python、FastAPI、SQLAlchemy、SQLite、Playwright、Jinja2/HTMX，保留 uv/Conda 与 Docker 运行方式。
用户进一步确认：媒体输入数量由用户设置且展示代价；采用有界分阶段流水线提速，各硬件敏感并发可配置；
提供保守推荐和设备检测建议；全站交互优化但沿用现有简洁风格，不使用前端设计类技能；所有变化保持跨平台。

核心原则：先确认选项、价格及证据，再判断预算与性价比。未知不是零元，提取失败不是没有瑕疵。

非目标：自动询价、自动聊天、下单或支付；绕过登录／验证码／访问控制；穷举商家全部 SKU；
音轨理解和完整动态故障诊断；宣称兼容未经验证的所有闲鱼页面；重写前端或引入分布式服务。

## 2. 方案比较与选择

- A（用户选择）：分阶段建立规格／价格基础，再接入媒体证据，最后测量并优化。每阶段可测试、审查、回退。
- B（不采用）：同时替换全部抓取、数据和分析逻辑，末尾统一测试。集成风险大，难以定位回归。
- 技术实现采用结构化页面证据优先、确定性规则裁决，LLM 只辅助抽取文本声明与总结，不生成实际售价或虚构 SKU。
  全靠 LLM 推断型号和价格不能提供可核对证据；一开始绑定某一家原生视频 API 则限制现有模型兼容性。
- 调度方案比较：仅修补串行队列改动小但模型仍阻塞抓取；全面异步／分布式重写成本高、增加部署负担；
  用户已选择推荐的有界分阶段流水线（§6.1），保留有界队列用于公平性、去重和背压，不引入 Celery/Redis 作为运行前提。
- 页面继续使用服务端模板及小量 HTMX/JavaScript；改善状态保持与操作反馈，不引入新视觉系统或 SPA 框架。

## 3. 当前实现与必要改变

- `ListingData/ListingDetail/Listing` 只有图片列表，没有视频媒体契约；品相请求最多发送四张图片。
- `variants` 仅由价格区间生成“最低价／最高价”，不是真实可购买组合。
- 搜索标价在详情提取前就被预算过滤；它还用于价格走势、性价比、重推，可能错误比较不同规格。
- `_fetch_detail` 通常有描述就不刷新；现有商品重评未必更新规格与媒体。
- 网络、模型调用处于较长数据库会话内；需测量锁占用、浏览器启动、重复模型请求与关系查询次数。
- “重新上架”判断发生在 status 被设为 active 之后，是需以回归测试验证的疑点；有限搜索结果未见不等于已下架。
- 当前应用无用户认证。升级不扩大默认网络暴露范围，不借此次改造冒充解决多用户安全问题。
- 当前队列只有一个消费者，整轮执行完再固定等待 300 秒；抓取前抖动也占着任务执行通道。
  因此慢模型、媒体处理和纯等待会阻塞其他任务，需要拆分资源通道，而不是简单删除所有队列或无限开线程。
- `listings_detail.html` 的返回链接固定 `/listings`，卡片未传入来源参数；这解释页面返回按钮丢失筛选。
  浏览器原生后退、加载更多、HTMX 刷新恢复仍需浏览器回归验证，不能将静态检查等同于已复现全部症状。

## 4. 阶段一：规格与价格可信度

### 4.1 数据与职责

沿用按任务隔离的 Listing 父记录；保留 `Listing.price` 与旧 PriceSnapshot 为“页面标价／旧标价走势”，
不再把它们直接当作目标规格的成交价。新增规范化的选项和观察记录，不继续向无类型 variants 字典塞业务状态。

- WatchTask：新增独立的目标规格文本 `target_variant`（如“iPhone 15 / 256GB / 非扩容”）和 `notify_pending_price`。
- ListingOffer：`listing_id`、稳定 `offer_key`、原站 SKU ID（如存在）、规范化属性、选项名称、可用状态、
  当前价格状态／证据、匹配状态、评估结果。唯一约束 `(listing_id, offer_key)`。
- OfferObservation：关联 offer、原始来源、价格状态、确定价或区间、采集时间、页面位置／原文片段、内容指纹。
  新价格以人民币分整数保存；原始金额用 Decimal 校验后转换，拒绝负数、非有限值和不支持的币种。
- ManualQuote：关联 offer、金额、用户说明、确认／失效时间、撤销状态；独立于抓取值，绝不被爬虫覆盖。
- offer 维度的评估与通知记录：记录使用的 observation/quote、媒体证据和任务条件指纹；通知增加 offer 与事件类型引用。

原站 SKU ID 优先作为身份；无 ID 时按完整规范化属性组合生成稳定键，不依赖显示顺序或价格。
多个不同选项出现相同属性键、或无法确认组合完整性时标记歧义，不把它们合并。
普通单件无规格商品使用默认 offer；旧 variants 区间仍展示为历史信息，不能迁移为真实 SKU。
父 Listing 的摘要兼容旧 API，但新增明确的有效价格／规格／状态字段，前端不得再将旧 price 标成确认价。

### 4.2 价格状态与裁决

| 状态 | 含义 | 允许预算判断与性价比排名 |
| --- | --- | --- |
| exact | 当前具体可用选项有明确价格，且无适用的冲突或非售价声明 | 是 |
| range_or_from | 仅起售价或区间，目标选项未确定 | 否 |
| inquiry | 明示需咨询、标价非售价或占位价 | 否 |
| conflict | 同一选项同时存在互斥的价格声明 | 否 |
| unknown | 抓取失败、信息缺失或映射不明 | 否 |

另有“人工确认报价”来源，不将它伪装为原站 exact。exact 仅表示页面证据明确，不保证卖家最终履约价。
stock 状态使用 available/unavailable/unknown；SKU 不可用时不参与正常推荐，未知库存明确展示。
“起”本身不能推断高价规格售价；“优惠私聊”与“所有标价非实际售价”区分作用范围；
声明作用范围不清时保守待确认，不能让一个疑似数字覆盖其他明确证据。
来自图片或 LLM 的识别仅为待核对声明：必须关联证据，不独立提升为 exact。

### 4.3 采集与目标匹配

首先从商品所属 DOM／结构化页面状态读取真实 SKU 组合；只读必要的选项交互，不点击购买／咨询／支付。
支持的结构化状态格式需要真实样本验证，不预先假定平台存在某个 API。
最多处理每链接 20 个候选组合，只针对目标匹配选项做后续昂贵分析；限制截断时显示“规格获取不完整”。
规则负责型号、容量等可确定约束；LLM 可以提出映射候选，但不能把不确定候选标为已匹配。
没有填写 target_variant 时，普通单件照常处理；多规格商品显示已核对的选项，多个匹配项分别评估，不能默认最低价代表整件。
明确型号／容量不匹配不推送；目标匹配不确定则留待确认，不进正常排名。

搜索阶段只保留非价格的安全过滤与抓取数量上限。预算过滤在 offer 解析后进行，避免起售价提前漏掉目标规格。
默认每任务每轮最多 30 个详情候选；超过预算进入后续轮次的有界待抓取队列（持久化或可重建），记录未处理数量，不能静默当作不匹配。
明确要求规格核验而 fetch_detail 关闭时，保留待确认状态并提示该设置不能获得确价，不偷偷启用详情抓取。
exact 的单价落在任务预算内才进入正常候选；待确认价不以标价判断超预算，不进入性价比模型／本批最优。
已知品牌或商家身份不作为直接排除条件；包装、配件、整机作为不同选项匹配，避免交叉借用证据。

### 4.4 人工报价与通知（下列默认值为本设计提议）

- 待询价商品默认站内保留，独立的待确认提醒开关默认关闭，避免升级后突然增加外部通知；用户可按任务开启。
- 手动报价必须绑定明确规格；确认页面同时展示最新抓取的价格证据，默认有效期 7 天，可修改或撤销。
- 人工报价有效且规格匹配时可用于预算和排名，所有结果注明“人工报价”和确认时间。
  新抓取的同 SKU 价格／非售价声明有实质变化时，旧报价转为需复核；选项不可用或身份歧义也会使报价不可用于推荐。
- 当人工报价与页面 exact 同时有效，优先采用用户对照最新页面证据确认的人工报价（人工操作页明确提示该优先级）；
  该报价必须记录确认时的页面证据指纹。若页面证据实质变化，先暂停人工报价而不是偷偷切回页面价继续推送。
  用户复核或撤销后才重新确定有效来源。页面价与人工报价的历史分开比较；两种来源切换仅称“价格来源更新”，
  不标为降价，同来源内的新价格与旧价格可比时才计算降幅。人工报价到期后可采用仍新鲜的页面 exact，注明来源切换。
- 不同规格分别做同价历史比较；从 A 切换到 B 不能叫“降价”。历史证据保留，不覆盖。
- 预算、规格或关键需求修改使评估失效；重评不沿用旧目标报价，不复用旧任务条件的评分。
- 通知以 offer、事件类型、证据／评估版本、渠道记录状态；待确认转明确可触发一次正常提醒。
  相同待确认状态与证据不重复推送；渠道失败单独记录，不将其他成功渠道重新发送。
  不声称网络超时情况下能严格 exactly-once；无幂等接口的渠道需提示可能重复，避免无限重试。
- 未知价格只展示需求和媒体分析的独立结果，不产生可与正常候选混排的综合性价比名次。

### 4.5 刷新与页面行为

任务表单、API、设置、列表、详情和通知统一使用价格解析服务输出；不在模板另写价格裁决。
详情提供规格明细、页面标价与有效价格的区分、原文依据、人工报价的新增／撤销操作。
普通列表仅将确价候选纳入默认性价比排序；待确认独立筛选，预算／价格排序不拿占位价填空。
SKU 与有效价格最多缓存一个调度间隔，手动重新分析和刷新强制更新；人工报价独立保持。
下次抓取失败不抹除旧证据，但将其标为旧观察，不把该轮故障视为库存变化或降价。
价格、规格映射与可用状态的核验有效期为一个任务调度间隔，自最后成功核验的时间计算；
短暂失败不提前缩短这个有效期，但该失败本身不产生新的价格事件或提醒。
任一必要证据到期后，该 offer 转为待复核并暂停正常排名与正常外部提醒，不删历史记录、不重新认定售罄。
人工报价的七天有效期只描述报价本身，不能代替新鲜的规格／可用状态证据；暂停推荐不会撤销或缩短报价期限，
后续成功核验无实质变化时可在原有效期内恢复。恢复不凭状态变化重复发送已成功的事件。

## 5. 阶段二：视频及图文混合证据

### 5.1 媒体契约

MediaAsset 记录 listing/可选 offer、image/video/frame 类型、原始来源／页面位置、封面、时间位置、内容 hash、
采集时间、父视频引用、处理状态与失败原因。没有确切 SKU 关联时标记 listing_shared，不假设属于任意一台机器。
只采集商品详情主媒体区域，排除推荐流、头像、广告；不能只按整个网页的 video/img 标签抓取。
视频 URL 可能过期、blob 或为分段流：首版支持可授权获取的直接 HTTP(S) 媒体；blob/DRM/未适配流清楚标注不支持，
不绕过权限。必要时通过正常页面刷新重新获取临时 URL。

### 5.2 抽帧与资源边界（设计默认值，可配置）

使用 FFmpeg/ffprobe 子进程处理本地受限文件，再把帧转为现有视觉接口支持的图片输入；不要求特定厂商的原生视频 API。
Docker 显式安装 FFmpeg；uv/Conda 检测外部工具，缺失时禁用视频处理并提示安装，不让应用无法启动。
视频分析为明确开关，默认关闭且显示“未分析视频”；启用后与图片联合分析。以下均为可见、可配置、服务端校验的资源预算，
不是靠前端隐藏或硬编码数量决定：

| 设置 | 默认 | 第一版允许范围 | 代价与语义 |
| --- | --- | --- | --- |
| 每商品原图保留数 | 8 | 1–32 | 下载／存储增加，不等于每张均分析 |
| 每商品视频数 | 1 | 1–3 | 每个视频分别占下载／解码预算 |
| 每视频保留采样帧数 | 6 | 1–24 | 解码耗时、磁盘与证据量增加 |
| 每请求原图配额 | 4 | 0–16 | 更多图片通常增加模型用量和延迟 |
| 每请求视频帧配额 | 4 | 0–16 | 同上，抽帧不代表完整理解视频 |
| 每请求总视觉输入上限 | 8 | 1–16 | 必须不大于用户所选模型已知支持限制 |
| 视频文件上限 | 100 MiB | 10–200 MiB | 流式按字节截止，不只信 Content-Length |
| 视频时长上限 | 180 秒 | 15–300 秒 | 超限明确跳过，不偷偷分析前段后冒充全部 |
| 缓存总量 | 1 GiB | 256 MiB–10 GiB | 占用部署机器／容器挂载卷磁盘 |

混合媒体默认先给原图和视频帧各 4 个名额，按清晰度、去重和覆盖性确定顺序；单一媒体可借用另一类型未使用的名额，
但不能突破总上限。有混合媒体时，某类配额设 0 即用户主动不分析该类，结果必须显示该覆盖限制。
每类配置配额之和可大于总上限；混合场景按原图／帧交替公平分配至总上限，固定顺序使结果可复现，
默认自然得到 4+4；额外素材保留作证据。无任何可选输入时不发起伪视觉请求。
仅调整数量不自动拆成多个付费请求、不自动提升并发；执行一次品相评估仅使用一个选定媒体批次。
模型图像上限未知时保守限定在 8，用户可在高级设置显式确认其模型上限（最高 16）；
已知不支持该值时拒绝配置，不伪称所有 OpenAI 兼容服务支持相同图片数。
提高数量前提示费用／响应延迟／内存／下载及模型超限风险，展示配置前后输入上限变化；无提供商账单信息时不伪造金额。
默认将模型图片缩放至最长边 1280 像素、限制图片解码像素和请求体大小（默认 16 MiB，最高 32 MiB），
超限时停止该批评估并提示降低设置，不能静默删掉证据后仍标为完全分析。
这些配置纳入 Settings、设置表单、`.env.example` 与评估缓存指纹，重启后保留。

流式下载默认最多 60 秒、解码默认最多 30 秒（均可在高级设置 10–120 秒内调整），超预算中止并删除半成品；
媒体处理默认并发 1，FFmpeg 默认每进程 1 个解码线程；可调范围见 §6.2。
有限采样覆盖起、中、末，过滤模糊／重复帧；不宣称未采样片段已检查，也不对音频或动态故障下确定结论。
下载器验证 URL、DNS 解析地址和每次重定向；禁止回环、内网、链路本地、云 metadata 等目标。
媒体下载与可配置内网模型地址是不同信任边界；不用媒体请求携带任意域 Cookie。子进程不经 shell，
FFmpeg 仅读本地输入、限制网络协议和执行时间；文件输出在受控缓存根目录内。

### 5.3 缓存与证据分析

缓存位于 data/media-cache，默认上限 1 GiB、保留 7 天（可设 1–30 天）；原视频成功抽帧后删除，失败半成品立即清理。
该总上限包含原图、保留帧、下载半成品、处理中视频及其他磁盘中间文件，不另设不受控临时目录。
媒体任务开始前按有界下载大小和输出文件预算预留空间，所有读写共用配额记账；
先清理无占用的过期／LRU 文件，仍不足则延后任务并显示磁盘受限，不突破用户上限。
活跃任务的输入／输出保留占用引用，不被清理器删除；结束／失败／进程恢复核对并释放预留。
小缓存与高并发不能同时满足时降低实际派发并发；若单任务最坏所需空间都无法容纳，拒绝该配置组合或要求降低文件／采样预算，
不进入永远无法启动的等待。设置页解释配置并发与磁盘允许的有效并发，避免“256 MiB 缓存却同时下载两份 200 MiB”。
同时检查磁盘剩余空间并预留系统安全余量；外部进程占用导致空间不足时失败清理，不能承诺控制整块磁盘的使用量。
按内容 hash／处理参数去重，媒体 URL 改变不直接认定内容改变；无法取得内容时不可凭 URL 缓存成成功。
已被分析引用的帧若因容量被清理，保留摘要、hash、时间位置并显示“证据文件已清理”；可重新获取，不显示坏链接。
API 不接受任意本地路径；媒体通过受控 ID 映射提供，不泄露签名 URL 的令牌、Cookie 和宿主文件路径。
模型请求使用可验证的 data URL 或受支持上传，不把容器本地文件路径传给远程模型；现有 chat/responses 两接口都要覆盖测试。
分析输出包括证据 ID、来源、视频时间位置、观察到的瑕疵、卖家声明、信息冲突和未验证项。
结构化校验只允许引用本次输入的证据 ID；拒绝模型虚构的帧、价格、容量或来源。
共享媒体不能自动生成某一 SKU 的确定品相结论；分析结果保留样品／不保证对应实物提示。
抓帧或模型失败时保留可用图片分析；无有效视觉证据时不生成“品相达标”结论，正常提醒明确标识未核验。
最低品相分是明确门槛：任务设置大于 0 时，必须有适用于该 offer 的有效视觉评分达到门槛，
未分析、分析失败、只有不确定关联的共享样品媒体均进入待核验，不参与正常排名或正常外部提醒。
最低分为 0 时，确价且规格匹配的商品可在明确标注“品相未核验”的情况下按价格等已知信息排名／提醒，
但不能生成品相通过结论。媒体与文字有实质冲突时保留冲突状态，不能用缺失分数的默认半分掩盖。
关闭视觉而任务最低分大于 0 时提示配置冲突，不能静默放行或修改用户门槛；这是相对于旧放行逻辑的有意行为改变。
评估缓存包含证据内容、任务条件、模型／提示词版本；变更时失效。支持手动强制重评，避免陈旧结论。

## 6. 阶段三：全项目检查、性能与缺陷修复

先建立可重复的基线，再按实测瓶颈修复；不承诺“没有任何 bug”或给出未测量的提速比例。

- 正确性：重新上架、有效价格变化、规格售罄、部分解析失败、重评、暂停／删除任务、通知失败恢复。
- 生命周期：有限搜索结果未见只能称“本轮未见／疑似不可用”；只有详情确证下架才标为确定下架。
- 数据库：外部请求不占写事务；按商品／步骤短事务，迁移失败不留下半套新结构；验证并发读写与 N+1。
- 浏览器：按 §6.1 的所有权规则复用浏览器／隔离上下文，取消／异常可靠关闭；平台访问限速独立于分析并发。
- 模型：同证据不重复分析；有限超时、退避、重试与单任务调用预算；预算耗尽保留待处理状态，不误报否定。
- 可观测性：每轮记录候选数、详情耗时、媒体耗时、LLM 次数、缓存命中、SQL 次数和失败状态；日志屏蔽秘密。
- 安全回归：表单先校验后提交、敏感配置与运行时配置边界、媒体下载边界、noVNC 默认关闭、路径穿越。

用固定的合成／脱敏商品集和 mock 网络／模型做可重复基准，比较冷启动与第二轮热缓存：
热缓存不重复启动每商品浏览器、不重复相同媒体的模型分析；记录中位数与 P95、查询数、调用数和资源峰值。
任何优化需证明结果一致、无重复通知、无明显回归；绝不为性能提高抓取频率或取消安全等待。

### 6.1 有界分阶段流水线

APScheduler 仅提交到期信号，不直接执行完整任务；人工重新分析也走同一资源管理器。
单进程协调器管理持久化 Run/WorkItem（含任务版本、阶段、输入指纹、重试时间、运行租约和状态），
阶段为搜索／详情抓取 → 纯解析与规则裁决 → 可选媒体处理 → 模型分析 → 聚合与写入 → 通知投递。
配置、凭据不复制到工作项；工作项仅保存必要引用和脱敏错误。线程池适用于网络 I/O，视频用受限子进程，
不为简单 HTML 解析创建大量 CPU 进程，也不使用 OS 专属 fork 实现。

- 抓取通道默认单 worker：该线程创建并拥有 Playwright 及浏览器，其他线程不访问这些对象。
  可配置最多两个抓取 worker，各自拥有完整独立生命周期；每次抓取／任务使用隔离 context，完成后关闭。
  浏览器按有限寿命与错误情况回收，不跨线程共享页面或持有宿主登录窗口。每账号同时平台导航最多 1，
  即使抓取 worker 增为 2 也不增加同账号并行导航；额外 worker 不是鼓励多账号绕过限制。
- 平台请求间隔、429／验证码退避在账号级统一生效；默认最小导航间隔 10 秒，高级可在 5–300 秒内设置。
  不再在整个任务结束后无条件等待 300 秒；等待下一次允许访问时不占用模型或媒体槽位。
  抖动改为调度器上的 not-before 时间，不用 sleep 占着整个任务执行槽。
  更低间隔可能增加风控和账号限制风险，需明确提示；平台风险反馈可延长间隔，不能自动缩短用户值。
- 模型通道独立线程池与全局并发上限；可设 RPM 限额（默认 10，范围 1–60），重试也计入。
  每请求 timeout、最多 2 次重试，指数退避不占 worker 槽；并发不会绕过 RPM 或提供商返回的 Retry-After。
  未知厂商限额按保守值处理；已知更低限额优先，不能自动以设备强大为由提高 API 访问量。
- 解析输出和模型输出为不可变 DTO，线程不传递 ORM 对象／数据库 session。协调器单写入路径，
  写事务短且无外部网络调用；读请求用独立 session。SQL/SQLite 忙等待有限，重试时重新核验任务版本。
- 所有通道有界：默认全局最多 200 个未完成 WorkItem，每任务最多 60 个；达到上限暂停上游生产。
  搜索候选和下一轮待处理项去重持久化，超过上限以未完成运行游标／受限剩余 ID 集恢复，
  不把未处理项当作“不匹配／下架”，不让内存无限积压。任务间轮转公平，单任务不会占满所有槽位。
- 每任务同时仅一个 active run；运行中再次触发只合并为一次后续到期信号，不并行跑同任务。
  默认同时 active run 数低占用和均衡均为 2（最高 4，可手动降到 1）；active 仅表示允许跨任务分阶段推进，
  实际资源占用仍由各通道限制。进程启动按租约恢复已完成与未完成步骤，不整轮盲目重做。
  等模型／退避的 run 保持 active 身份，但不占抓取槽；默认两个 run 足以使慢模型期间另一任务能抓取。
  用户主动将 active runs 设为 1 时明确说明会退化为跨任务串行，跨任务重叠验收仅在 active runs 至少 2 时适用。
- 预算默认每 run 最多 30 个详情、60 个模型 HTTP 尝试（含重试）、15 分钟墙钟期限；
  高级允许分别 1–100、1–200、5–60 分钟。到期后未完成步骤延后至下一次运行，不硬杀共享线程。
  网络与子进程有独立硬超时；到期／取消后回来的迟到结果不得提交。
- 暂停任务：停止新调度，取消该任务待执行工作，活跃请求协作结束；恢复后按正常调度重建未完成工作。
  修改预算／规格等任务条件时递增任务版本：旧工作返回后只可保存为旧证据，不能覆盖新评估或发送通知。
  删除任务撤销其工作；每次发布结果与写入前用 Run ID + 任务版本 + 租约进行条件检查。
- 聚合不等待整批所有任务：仅针对当前 run 已就绪、确价、门槛通过的 offer，按批次生成局部比较。
  每 offer 的正常通知须等该 offer 的需求、价格和品相门槛都定稿；批次“最优”标记须注明比较范围，
  不把未完成候选当作低分或断言全市场最优。
- 通知先写持久化待投递事件，再在受限 I/O 通道发送；通知投递与业务计算解耦，
  相同业务事件的成功渠道不重发。进程崩溃后的未知投递结果标记 uncertain，默认等待人工重试，
  不无限自动重发不支持幂等键的渠道；新系统不保证外部网络严格 exactly-once。

生命周期补充：
- 计算 run 的租约／截止时间约束计算 worker 的结果提交；通知事件有独立投递租约，已合法提交的事件在 run 完成后可继续投递。
  run 超时不撤销此前成功提交的评估事件，也不允许超时后产生新评估事件。
- 通知每次发送前重新核对任务存在／启用、当前任务版本、评估有效性和必要价格证据新鲜度；
  任务暂停／删除／条件改变时撤销尚未发送事件；证据过期转为 awaiting_revalidation。
  已开始的外部 HTTP 发送不能保证撤回，明确记录 sent/failed/uncertain，不把已发送历史改成未发生。
- uncertain 的人工重试也先重新核验；证据已旧则不能直接发出旧推荐。重新核验未实质变化时恢复原业务事件，
  不创建重复通知；证据变化时原事件标为 superseded，并按新证据是否满足条件决定创建新事件。
- “仅恢复未完成步骤”不代表永远复用已过期结果：跨轮／重启恢复前检查任务版本及各步骤依赖指纹和新鲜度。
  先刷新过期的价格／规格／可用性；若只是观察时间更新、实质内容未变，复用仍符合内容指纹的媒体／模型结果，
  不重复付费分析；实质内容变化才失效受影响的下游步骤。
  恢复工作挂入当前有效 run，用当前已核验的观察记录建立评估引用；旧 run 历史保持不可变。

### 6.2 用户资源设置与推荐配置

任务调度与硬件敏感设置全部可见、服务端有范围校验；资源 profile 只是填写配置的快捷方式，不是第二套隐形配置。
平台访问间隔、模型 RPM 和每轮预算不是设备检测可自动放宽的设置。

| 项目 | 低占用／首次启动默认 | 均衡（用户确认后） | 自定义硬上限 |
| --- | --- | --- | --- |
| active runs | 2（可手动降为 1） | 2 | 4 |
| 抓取 workers | 1 | 1 | 2（每账号导航仍为 1） |
| 模型请求并发 | 1 | 2 | 8 |
| 媒体处理并发 | 1 | 1 | 2 |
| 每个 FFmpeg 线程数 | 1 | 1 | 4 |
| 平台导航最小间隔 | 10 秒 | 10 秒 | 见 §6.1，不随设备调整 |
| 每请求图像上限 | 8 | 8 | 16，且受模型限制 |

第一版不提供“一键最高性能”，避免把强硬件误认为可忽略平台和模型限流。并发增加会提高浏览器内存、
请求排队、视频 CPU、模型费用消耗速度与 SQLite 竞争；提高线程数不承诺线性提速。
资源保护优先级：应用硬上限／容器资源边界 > 用户已确认的资源上限 > profile 默认。
运行时压力过高只可临时降低有效并发并显示原因，不偷偷改保存值；不会自动提升至未确认值。

硬件检测只读、本地执行，不上传硬件标识、不跑压力测试：
- Windows/macOS/Linux 检测 CPU 数、总内存和可用内存；可采用跨平台 psutil，依赖与镜像锁同步。
- Linux 容器结合 cgroup v1/v2 的 CPU quota、cpuset、memory limit/current 与进程可用资源取较小可用值；
  可获取亲和性时也纳入。无限制、缺文件、权限不足、嵌套容器等情况显示检测依据／不确定性，不能拿宿主全量资源做保证。
- 首次默认低占用；当有效 CPU 至少 4、有效内存上限至少 6 GiB、当前余量至少 3 GiB 时才建议均衡。
  不满足或检测不完整建议低占用。保存建议前展示检测时间、容器／本地来源、拟变更字段和代价，用户点击确认后生效。
- 不检测 GPU 或自动启用硬件解码；GPU/显存不是远程模型推理能力的可用资源。

配置变更按版本应用：只影响新派发工作。减少并发先停止派发、让当前请求结束再缩容，
媒体数量／模型变化使后续评估缓存失效，不自动批量付费重跑全部历史商品。
外部 API 的有效 RPM／超时设置也记录在可见配置中；无有效值时拒绝保存，不以 0 表示无限。
模型输入数量与资源预算都由同一 schema 供 UI/API/env/worker 使用，避免设置表有值而执行器不读取。

### 6.3 全站交互整理（不更换视觉风格）

沿用现有简洁配色、按钮、字体和服务端模板；不使用前端设计类技能，不增加炫技动画、厚重组件库或 SPA。
此次重心是导航、状态保持、分类、操作反馈和移动端可用性，不改变产品品牌或信息架构的基本入口。

列表上下文以规范化 URL 查询为事实来源，覆盖 task_id、价格可信状态、show、sort、分页／已加载范围。
点击详情携带经过白名单构造的相对 return_to；详情返回、拉黑、恢复、删除、重新分析后回到原上下文。
仅允许本站指定列表路径及合法参数，防止开放重定向；无来源时回标准列表，不能直接使用任意 Referer。
浏览器原生后退／前进、刷新、直接粘贴链接都应得到一致筛选；滚动锚点和加载范围按查询键存在 sessionStorage，
不能跨查询错误恢复。恢复范围有上限，分段加载，商品被删除时返回相近位置而非空白页。
不承诺动态数据集永远回到同一像素，但必须保留用户筛选和排序；登录 Cookie、密钥不进 URL/浏览器状态。

加载更多与 HTMX 刷新共享参数构造器、稳定排序键（加 ID 做同分 tie-breaker）和去重规则。
自动刷新不重置加载范围／滚动／筛选、不清掉用户已选项，不替换正在编辑的表单；
交互期间可暂停刷新并显示“有新结果，点击更新”，不能靠每两秒整页换 DOM 达到实时。
全选明确表示“已加载可见结果”，不默默选择整个数据库；危险操作确认显示数量，失败时保留选择及筛选。

设置按账号与登录、文本／视觉模型、消息通知、抓取与性能、媒体、部署与诊断分组；
类别使用锚点／轻量 tab（移动端可用），不是视觉重做。支持直接链接到分类，当前分类刷新／返回后保持。
每分类独立保存，未提交分类不改；复选框仅在该分类的字段白名单内解释未勾选，
密钥留空保持原值，清除须显式确认。未保存更改切换分类／离开时提示，失败保留非敏感输入，
秘密不回显到 URL、localStorage、日志或 HTML 明文。浏览器及服务端都校验，失败不写半套配置。
部署／启动级字段（数据库路径、绑定地址、容器运行模式等）只读或明确说明需改 env／重启，
不能把所有 Settings 字段无差别当作可从 Web 修改的运行时选项。

页面范围与行为验收：
- 仪表盘：区分排队、抓取、分析、待询价、待核验、失败；数字与任务状态一致，不显示虚假进度百分比。
- 任务列表／详情：新增目标规格和待询价开关；运行按钮防重复提交，暂停／取消语义与 §6.1 一致，
  编辑保存后留在当前任务／原列表位置，清楚反馈是否有旧版本工作被取消。
- 商品列表／详情：保持筛选与位置，区分标价／确价／人工报价和证据来源；未知价格不展示为 0 或“超值”。
- 消息通知：保留筛选／分页，区分 pending/sent/failed/uncertain，重试仅影响所选渠道，不能靠前端刷新伪造成功。
- 设置：分类、局部保存、配置代价、设备建议确认和生效范围；缺视频工具或模型上限不明时有操作指引。
- 全局：统一加载、空结果、错误／成功反馈；错误 HTTP 响应不能被当作成功后直接 reload；危险操作确认、键盘可达、
  窄屏表单／导航无横向溢出。无 JS 时核心筛选和表单提交仍能用；恢复滚动等增强可降级。

### 6.4 分阶段顺序、基准与发布边界

执行前先记录原行为与失败案例、建立隔离测试配置和性能基线；随后：
1. 规格／价格域及兼容迁移（阶段一），先稳定正确性。
2. 媒体证据与可配置输入预算（阶段二），默认不增加付费视频请求。
3. 有界流水线与资源配置（阶段三前半），将前两阶段接入统一执行器；旧执行器仅在过渡测试使用，
   交付时不得同时消费相同工作。再完成交互整理、性能对比、全项目缺陷修复与最终验收。

使用隔离数据库、固定合成媒体和 fake 平台／模型时钟测试；不以真实平台压测来证明性能。
关键场景为慢模型下下一任务抓取仍可在平台节流允许后推进、并发峰值永不超过配置、压力降档不丢工作、
任务版本变化拦截迟到写入／通知、重启仅恢复未完成步骤、挂起任务不会饿死其他任务。
浏览器交互验证使用 Playwright 等功能测试，不调用前端设计技能；Windows 本地＋Linux Docker 为实测目标，
macOS 及其他架构未实际运行须标注验证边界，不能因“跨平台库”就声称所有设备已测过。
设计与实现均不新增操作系统专属启动前提；Linux 容器只读资源检测是能力增强，本地检测失败必须可降级。

## 7. 迁移、兼容与回退

开发和 Docker 验证使用独立数据库、缓存、容器名和未占用的回环端口，禁止挂载生产 data/；默认禁用真实通知与定时任务。
生产升级前停写并制作可恢复备份；迁移按版本、幂等、事务执行，先验证临时旧库副本，不能运行未备份的破坏性迁移。
新增表与字段保留原数据；旧评分标记 legacy_unverified，不转换为新规格的确定结论；原有通知历史不触发重发。
旧任务 target_variant 为空、待询价外部通知关闭；旧单件下次成功详情抓取后生成默认 offer，未知 SKU 不凭区间构造。
旧安装升级时保留原有每请求最多 4 张的视觉输入预算，视频仍关闭；新安装默认总上限 8、混合配额 4+4。
迁移记录明确区分已有安装与新初始化，不能根据有没有 API Key 猜测；已有显式预算始终保留。
旧用户可在媒体设置中查看从 4 提升到 8 的代价并显式确认；启用视频或应用硬件 profile 不隐式提高媒体总上限。
低占用／均衡快捷配置只修改并发资源字段，媒体数量和视频开关另行确认，保持升级不默默增加模型用量。
任务删除、商品删除要覆盖新关联记录，防止孤儿数据；同一外部 ID 跨任务仍隔离。
关闭新视频能力不会影响原有图片功能；已升级数据库不承诺直接降级可写，完整回退采用备份数据库与旧镜像成对恢复。
保留本机已忽略的 Windows 快捷脚本、私人文档和 .env；不提交凭据、真实数据库、视频缓存和个人资料。
当前仅提交设计到本地专用分支；实施前审查远程变化，实施完成不擅自更新 main、release、Tag 或 GHCR。

## 8. 验收与交付

每阶段：先失败测试 → 最小实现 → 单测／集成测试 → 独立代码审查 → 修复 → 再验证；再进入下一阶段。

必要验收用例：
1. 配件 99、128GB 1200、256GB 1500：目标 256GB 使用 1500，预算筛选与历史比较正确，绝不拿 99 评分。
2. 占位价 1 元、明确非售价或需询价：待确认、无性价比／本批最优，开关与去重符合约定。
3. 冲突价、选项售罄、SKU 身份变更、详情失败、组合超限不被静默视为已核验；人工报价不会被自动覆盖。
4. 同一规格降价才产生降价事件；不同规格切换、人工报价过期、条件变化均不冒充降价。
5. 图片、纯视频、混合媒体、样品视频、过期链接、超大小、超时、缺 FFmpeg、SSRF／路径穿越均有回归用例。
6. 旧库迁移两遍结果一致，任务／历史／快照／通知不丢失；备份恢复演练通过。
7. Ruff、锁文件检查、全套 pytest、覆盖率不低于现有 80% 门槛；关键新裁决分支需直接覆盖，不能只靠总覆盖率。
8. Docker 构建、SDK 导入、FFmpeg 检测、独立数据库启动、healthz、表单／详情／提醒预览与 noVNC 模式检查通过。
9. 提供性能基线与改后对比，未运行项和受外部环境限制的项如实列出，不以合成样本代替真实平台验证。
10. 媒体预算在 UI/API/env 一致，默认混合 4+4，单一媒体借额、不超过总上限；调整时展示代价，非法／超模型上限拒绝。
11. 调度去重、公平性、背压、队列上限、资源峰值、429 退避、退出重启、暂停取消、迟到结果、未知投递结果均有回归测试。
12. 容器限额覆盖宿主资源；检测失败推荐低占用；设备推荐不自动应用，也不提高平台／API 限额。
13. 商品筛选→加载更多→详情→返回、原生后退／前进、刷新、拉黑／删除／重评均保留上下文；设置分类保存不会修改其他分类。
14. 所有页面的加载／失败反馈、窄屏、无 JS 核心功能可用；保持原有简洁风格，不用前端设计技能。

真实平台适配需要合法可访问的多 SKU、询价、纯视频／混合媒体代表样本；采集夹具必须脱敏。
若缺真实样本可完成领域模型、规则与夹具测试，但不能将真实 SKU 自动提取／视频覆盖宣称完成；
相关能力保持实验性／待验证并明确列为交付限制，不自动启用或发布稳定版。

## 9. 待批准的提议与实施者可决定事项

待用户随设计一并批准：待询价站内保留但外部提醒默认关闭；人工报价默认 7 天；视频抽帧可选且默认关闭；
分阶段完成三个阶段（含新版流水线和全站交互），真实样本验证不足时明确标为限制而非伪造兼容结论。
以上默认值均为助手提议，不表示用户此前逐项确认。
同样待批准的裁决：有效人工报价优先但来源切换不算降价；新鲜度过期暂停推荐、保留报价；
最低品相分大于 0 时未核验不得进入正常推荐。实施计划必须显式覆盖这些变化与回归测试。
新版提议默认：首次使用低占用 profile（两个轻量 active run、每资源通道并发仍为 1），设备推荐需确认；
新安装媒体默认总上限 8、混合 4+4 可调，旧安装升级保留总上限 4，显式确认后才提升；
平台节流替代旧任务结束后的固定等待，导航默认间隔 10 秒、模型 RPM 默认 10；资源和输入硬上限如 §5.2／§6.2。
用户已确认方向与方案，但这些精确默认数值和完整生命周期规则仍随本设计一并批准。

实施者可决定：内部模块命名、索引具体形式、帧去重算法及可维护的采样细节、测试工具与基准夹具组织；
不得改变不自动联系卖家、不用未知价排名、不触碰真实数据、不默默扩大资源预算等边界。

## 10. 独立设计审查记录

已由独立工程师审查初稿，发现三个会影响实施的重要歧义：人工报价与页面价的优先级、刷新失败／过期后的推荐资格、
最低品相分对未核验商品是否构成硬门槛。已在 §4.4、§4.5、§5.3 补充确定规则，作为设计提议交由用户批准。
审查未涉及实现正确性；具体代码、真实平台样本与性能结果仍须在后续阶段另行验证。

修订版 2 再次独立审查发现五项实施歧义，现已补充：
1. 默认两个 active run、资源 worker 仍为 1；手动设为 1 时明确跨任务串行代价。
2. 通知采用独立投递生命周期，发送前重新核验任务版本／证据；完成计算不等于通知失效。
3. 跨轮恢复先校验过期依赖，内容不变复用模型结果，内容变化才重做相关分析。
4. 旧安装保留原每请求 4 张预算，新安装默认 8，硬件建议不默默改变媒体用量。
5. 磁盘总预算包含临时文件，预留空间与背压确保配置的缓存上限有意义。
以上补充均为助手提出的确定规则；用户已在本次对话确认修订设计，未开始实现。
