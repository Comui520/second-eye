# 第二轮：企业微信通知 + 分阶段筛选链路 + 稳定性修复 — 设计文档

## 目标

1. 新增企业微信应用消息通知通道（免费、推送到微信）。
2. 筛选改为两阶段流水线：需求匹配（文本）→ 视觉品相（看图），卖家信用下一轮。
3. 修复稳定性问题：立即执行后台化、防重入、错误友好、任务需求展示、调度即时同步、密钥不回显、缺失分析回填。

## 决策记录

- 筛选方案：分阶段流水线（方案 A）。
- 需求不匹配：直接不通知（不进入阶段二）。
- 描述来源：抓详情页 + 任务级开关（`fetch_detail`，默认开）。
- 卖家信用：下一轮。
- 企业微信形态：应用消息（corpid/agentid/secret/touser）。
- 视觉模型：强依赖（未配置视觉模型则跳过阶段二，不做文本假装看图）。
- 回填：只补字段，不重复发通知。
- 阶段一失败/详情抓取失败：不拦截（宁多勿漏），记录原因。

## 流程

价格初筛 → 新商品抓详情（可选）→ 阶段一需求匹配（文本，DeepSeek 可用）→
不匹配则丢弃 → 阶段二视觉品相（需视觉模型；未配置则跳过并注明）→
品相分低于门槛则丢弃 → 通知（日志/Server酱/企业微信）。

## 详情页 DOM（实测 2026-08-13）

- 描述：`span[class*='desc--']`（含 `<br>` 分段；`[class*='desc--']` 会误匹配价格描述，取文本最长者）
- 主图：`img[class*='ant-image-img']`（排除底部相关推荐的 `feeds-image--`）

## 数据变更

- `watch_tasks.fetch_detail`（BOOL，默认 1）
- `listings.description`（TEXT）、`listings.requirement_match`（BOOL）、`listings.requirement_reason`（TEXT）
- 幂等迁移：`PRAGMA table_info` 检查缺列 → `ALTER TABLE ADD COLUMN`
